## 三、架构决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | epoll 多 Reactor | 4线程×1250连接, 零争用 |
| 2 | Gap Buffer | 变长帧场景优于 Ring Buffer |
| 3 | 房间串行（无锁） | 单 LogicWorker 线程独占, 零竞争 |
| 4 | TCP 长连接 | 可靠传输需求, 内置流控 |
| 5 | Protobuf 协议 | 18B定长头 + varint载荷, Go手写解析器 |
| 6 | 连接池 (MySQL/Redis) | 4连接池替代单连接+互斥锁 |
| 7 | 异步操作队列 | 统一消除跨线程数据竞争 |
| 8 | 批量匹配出房 | `while` 替代 `if`, 1000 bots 瞬间匹配 |

## 四、数据竞争修复历程

| Phase | 竞争点 | 方案 | 效果 |
|---|---|---|---|
| P7 | Acceptor↔EventLoop | 连接待处理队列 | 5000 连接稳定 |
| P8 | onTick↔EventLoop | 写入待处理队列 | 30 bot 稳定 |
| P9 | EventLoop↔LogicWorker | 房间操作待处理队列 | 200 bot 稳定 |
| P10 | 匹配串行瓶颈 | 批量出房 | 1000 bot 战斗 |
| P11 | 线程启动 + Tick 统计 | 修复 + 埋点 | P50=50us |
